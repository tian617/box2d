# 01 · 整体框架：一座物理工厂

> 把 Box2D 想象成**一座汽车工厂**。这一章带你参观厂房，认识每个车间干什么、工件怎么流转。

## 一、全局俯瞰：World 里到底装了什么

`b2World` 是唯一的**上帝对象**。所有东西都以**数组 + 整数索引**的形式存在里面（没有 `new`、没有指针链表）。

```mermaid
graph TB
    subgraph b2World["b2World —— 世界容器（源码 src/physics_world.h）"]
        direction TB

        P1["<b>对象池（按 id 索引）</b><br/>bodies[ ] shapes[ ]<br/>contacts[ ] joints[ ]<br/>islands[ ] chains[ ]"]
        P2["<b>solverSets[ ]</b><br/>0=static 1=disabled<br/>2=awake 3..N=sleeping"]
        P3["<b>constraintGraph</b><br/>colors[0..22] + overflow[23]"]
        P4["<b>broadPhase</b><br/>trees[static/kinematic/dynamic]"]
        P5["<b>stack</b> 栈式分配器<br/>每帧一次性回收"]
        P6["<b>taskContexts[ ]</b><br/>每个 worker 一份位集"]
        P7["<b>事件数组</b><br/>bodyMove / contact<br/>sensor / joint"]
    end

    P1 <-->|"body.setIndex / localIndex"| P2
    P2 <-->|"contact.colorIndex / localIndex"| P3
    P1 -->|"shape.proxyKey"| P4
    P2 -.->|"每帧向 stack 借内存"| P5
    P3 -.-> P5

    style P2 fill:#30AEBF,color:#fff
    style P3 fill:#DC3132,color:#fff
    style P4 fill:#8CC924,color:#fff
```

### 为什么全是数组和索引？

**三个理由**：

1. **缓存友好**：求解器要遍历上千个接触，连续内存 + 预取 >> 指针跳转。
2. **可序列化 / 可确定性重放**：整帧状态就是一堆数组，可以直接 hash、存盘、回放（见 `src/recording*.c`）。
3. **可增长**：数组增长时对象在内存里搬家，但只要索引不变，外部持有的 `b2BodyId` 就还有效。

### ID 系统：为什么 `index1 = index + 1`？

```c
// include/box2d/id.h
typedef struct b2BodyId
{
    int32_t index1;       // 真实索引 + 1
    uint16_t world0;      // 世界 id - 1
    uint16_t generation;  // 代数（防悬挂）
} b2BodyId;
```

- `index1 = index + 1`：**0 表示无效 id**，这样 `b2BodyId id = {0}` 天然是"空"。
- `generation`：对象槽位被回收再利用时 +1。你手里拿着旧 id 去查，generation 对不上 → 立刻报错，而不是**静默地操作了另一个物体**。

```mermaid
sequenceDiagram
    participant U as 用户
    participant W as b2World
    Note over W: bodies[5].generation = 3
    U->>W: b2DestroyBody(id{6, w0, 3})
    Note over W: 槽位 5 空闲，generation → 4
    U->>W: b2CreateBody(...)
    Note over W: 复用槽位 5，id = {6, w0, 4}
    U->>W: b2Body_SetPosition(id{6,w0,3})  ❌
    W-->>U: B2_ASSERT 触发：stale id!
```

> **这就是 Box2D 相比 v2 最大的 API 改进**：v2 用裸指针，删了物体后指针变成野指针；v3 用 id + generation，立即能检测。

## 二、五个核心对象及它们的关系

```mermaid
erDiagram
    WORLD      ||--o{ BODY    : "bodies[]"
    WORLD      ||--o{ SHAPE   : "shapes[]"
    WORLD      ||--o{ CONTACT : "contacts[]"
    WORLD      ||--o{ JOINT   : "joints[]"
    WORLD      ||--o{ ISLAND  : "islands[]"

    BODY       ||--o{ SHAPE   : "headShapeId 链表"
    BODY       ||--o{ CONTACT : "headContactKey 链表"
    BODY       ||--o{ JOINT   : "headJointKey 链表"
    BODY       ||--o| ISLAND  : "islandId"

    CONTACT    }o--|| SHAPE   : "shapeIdA / shapeIdB"
    JOINT      }o--|| BODY    : "edges[2]"

    CONTACT    ||--o| CONTACT_SIM : "存在于 set 或 graph"
    BODY       ||--o| BODY_SIM    : "setIndex + localIndex"
    BODY       ||--o| BODY_STATE  : "仅 awake 集有"
```

用大白话说：

| 对象 | 一句话 | 生命周期 |
|---|---|---|
| **b2World** | 工厂 + 仓库 | 手动创建/销毁 |
| **b2Body** | 一个刚体（有质量、位置、速度） | 手动创建/销毁 |
| **b2Shape** | 贴在刚体上的一块形状（圆/胶囊/多边形/线段） | 挂在 body 上 |
| **b2Contact** | 两个 shape 的 AABB 重叠时**自动**产生的一对 | 自动增删 |
| **b2Joint** | 用户手动加的约束（铰链、弹簧、马达…） | 手动创建/销毁 |
| **b2Island** | 一群通过接触/关节连在一起的刚体（**只为睡眠服务**） | 自动合并/分裂 |

> ⚠️ **重要**：接触（Contact）**不是**你创建的，是引擎根据 AABB 重叠自动创建/销毁的。
> 这个观念转变很重要：Box2D 里"接触"是**一等公民数据**，会跨帧持久化（为了热启动）。

## 三、一个刚体被拆成了三份

这是理解 Box2D v3 数据结构设计的**钥匙**。

```mermaid
flowchart LR
    subgraph Cold["冷 · b2Body（用户 API 层）"]
        B1["userData<br/>name[11]<br/>type / flags<br/>mass, inertia<br/>headShapeId, headContactKey, headJointKey<br/>setIndex, localIndex<br/>islandId, sleepTime<br/>id, generation"]
    end

    subgraph Warm["温 · b2BodySim（每帧）"]
        B2["transform (位置+旋转)<br/>center (质心世界坐标)<br/>rotation0, center0 (上帧，给 TOI 用)<br/>localCenter<br/>force, torque<br/>invMass, invInertia<br/>minExtent, maxExtent<br/>linearDamping, angularDamping<br/>gravityScale"]
    end

    subgraph Hot["热 · b2BodyState（每子步 ×N 次）<br/>── 32 字节，SIMD 友好 ──"]
        B3["linearVelocity (8B)<br/>angularVelocity (4B)<br/>flags (4B)<br/>deltaPosition (8B)<br/>deltaRotation (8B)"]
    end

    B1 -->|"setIndex + localIndex"| B2
    B2 -->|"awake 集里同一下标"| B3

    style B3 fill:#DC3132,color:#fff
```

### 为什么要这么拆？

**答案：缓存行。** 一个缓存行 64 字节。

- `b2BodyState` 恰好 **32 字节** → 一个缓存行装 2 个，SIMD gather 一次能取 4~8 个。
- 求解器一个子步里要访问同一个 body 的 `v/w` 好几次（热启动、N 次求解、松弛、积分）。
  如果和 `userData`、`name` 混在一起，每次访问都要多拉几个缓存行，**几万倍地放大**。

### `b2BodyState` 里为什么是 delta 而不是绝对位置？

```c
typedef struct b2BodyState
{
    b2Vec2  linearVelocity;
    float   angularVelocity;
    uint32_t flags;
    b2Vec2  deltaPosition;   // ← 增量，不是绝对位置
    b2Rot   deltaRotation;   // ← 增量，(c,s) = (1,0) 表示没转
} b2BodyState;
```

**三个理由**（源码 `body.h:126-151` 有详细注释）：

1. **静态/运动学物体没有 state**。求解器对它们用一个"哑元 state"：`{v=0, w=0, Δp=0, Δq=(1,0)}`。
   用增量 → 哑元天然是"没动"，不需要任何分支。
2. **远离原点时精度高**。`deltaPosition` 是小量，绝对位置可能几千米（float 精度只有 ~7 位有效数字）。
   位置更新在帧末用 `b2OffsetPos`（双精度大世界模式）一次性加上去。
3. **避免多线程写冲突**。静态物体的 state 被多个线程同时读，如果大家都写同一个绝对位置（哪怕写同样的值），
   会引起缓存行乒乓（false sharing）。用哑元 + `b2_dynamicFlag` 判断，写操作被完全跳过。

```mermaid
flowchart TB
    subgraph Static["静态物体（无 state）"]
        S1["b2BodySim（有 transform）"]
        S2["哑元 b2BodyState<br/>v=0 w=0 Δp=0 Δq=(1,0)"]
        S1 -.->|每个线程本地栈上造一个| S2
    end
    subgraph Dyn["动态物体"]
        D1["b2BodySim（有 transform）"]

        D1 <--> D2
    end
```

## 四、求解集（Solver Set）：物体的"工位分区"

这是 v3 相对 v2 的重大重构。**世界被切成若干个"集合"，每个集合是一份完整的 sim 数据**。

```mermaid
flowchart TB
    subgraph Sets["solverSets[ ]"]
        direction LR
        S0["<b>[0] staticSet</b><br/>bodySims（无 state）<br/>jointSims（静态-静态关节）"]
        S1["<b>[1] disabledSet</b><br/>bodySims + jointSims<br/>禁用物体，不参与模拟"]
        S2["<b>[2] awakeSet</b><br/>bodySims + bodyStates<br/>islandSims<br/>contactSims（<i>未接触</i>的）<br/>── 有 state 的唯一集合 ──"]
        S3["<b>[3] sleepingSet A</b><br/>bodySims + jointSims<br/>contactSims（含 manifold！）<br/>islandSims"]
        S4["<b>[4] sleepingSet B</b><br/>…另一个睡着的岛…"]
    end

    W["b2Body"] -->|"setIndex, localIndex"| Sets

    style S2 fill:#DC3132,color:#fff
```

**关键设计点**：

1. **只有 awakeSet 有 `bodyStates`**。睡着的物体不需要速度。
2. **只有 awakeSet 的接触存在约束图里**；睡着的接触躺在自己的 set 里（带着 manifold 和冲量，醒来时直接继续）。
3. **每个睡眠岛一个 set** → 唤醒单个岛是 O(1)：把 set 内容搬到 awakeSet 就行，不用遍历世界。

```mermaid
flowchart LR
    subgraph Before["唤醒前"]
        A1["awakeSet<br/>[A][B]"]
        A2["sleepingSet#7<br/>[C][D][E]<br/>contact C-D, D-E"]
    end
    subgraph After["唤醒后（b2WakeSolverSet）"]
        B1["awakeSet<br/>[A][B][C][D][E]<br/>（C-D, D-E 进入约束图）"]
        B2["sleepingSet#7<br/>（空，被销毁）"]
    end
    Before -->|"C 被撞了一下"| After
```

> 源码：`src/solver_set.c` 的 `b2WakeSolverSet` / `b2TrySleepIsland` / `b2MergeSolverSets`。

## 五、约束图（Constraint Graph）：求解器的"工位排班表"

求解约束最大的障碍是**数据竞争**：两个约束碰同一个刚体就不能并行。
Box2D 的解法是**图着色**（Graph Coloring）——经典算法问题，这里用来做并行调度。

```mermaid
flowchart TB
    subgraph G["constraintGraph.colors[0..23]"]
        C0["colors[0]<br/>bodySet 位集<br/>contactSims[]<br/>jointSims[]<br/>wideConstraints（SIMD 临时）"]
        C1["colors[1]<br/>…"]
        CN["…"]
        C22["colors[22]<br/>（高优先级：静态接触）"]
        C23["colors[23] = OVERFLOW<br/><i>无 bodySet，单线程兜底</i>"]
    end

    style C23 fill:#8B0000,color:#fff
    style C22 fill:#006400,color:#fff
```

### 染色算法（`constraint_graph.c:67-135`）

```mermaid
flowchart TD
    Start(["新接触加入"]) --> Q{"两端都是<br/>动态刚体？"}
    Q -->|"是（dyn-dyn）"| D1["从 colors[0] 往上找<br/>范围 [0, B2_DYNAMIC_COLOR_COUNT=20)<br/>找一个<b>不含 A 也不含 B</b> 的颜色"]
    Q -->|"否（dyn-static）"| D2["从 colors[22] <b>往下</b>找<br/>找一个不含那个动态体的颜色"]
    D1 --> Found{"找到了？"}
    D2 --> Found
    Found -->|"是"| OK["加入该颜色<br/>并在 bodySet 里置位 A、B"]
    Found -->|"否（太拥挤）"| OF["丢进 colors[23] 溢出槽<br/>单线程求解"]
    OK --> End(["完成"])
    OF --> End
```

**为什么静态接触从后往前分配、动态接触从前往后？**

```
colors:  [0 ... 19]           [20][21][22]   [23]
          ↑dyn-dyn 用           ↑dyn-static 用  overflow
          （优先级低）           （优先级高）
```

求解时按颜色 **0 → 22** 顺序执行，所以静态约束**最后算**。
原因（源码注释 `constraint_graph.h:22-24`）：

> *"This keeps constraints involving two dynamic bodies at a lower solver priority than constraints involving a dynamic and static bodies. This reduces tunneling due to push through."*

人话：**先让物体之间互相推挤，最后再统一压到地面上**。如果反过来，地面先把物体压住，物体之间的挤压就来不及解决，容易被挤穿地面。

这是本章的**核心图**，请记牢。

### 阶段 4 的内部（子步进循环）

```mermaid
flowchart TB
    P["<b>Prepare</b>（只做一次）<br/>prepareJoints / prepareContacts<br/>→ 算出 anchor、有效质量、baseSeparation、softness"]

    P --> Sub["for subStep = 0 .. N-1 （h = dt/N）"]

    subgraph Loop["每个子步"]
        direction TB
        L1["① IntegrateVelocities<br/>v += h·(invM·F + g·scale)<br/>w += h·invI·τ<br/>再乘阻尼系数 1/(1+h·c)"]
        L2["② WarmStart<br/>把上帧的冲量重新打一遍<br/>（本子步的初值）"]
        L3["③ Solve（ITERATIONS=1，useBias=true）<br/>按颜色 0→22 并行求解<br/>法向：带 bias 的非穿透"]
        L4["④ IntegratePositions<br/>速度限幅 → Δp += h·v<br/>Δq = integrate(Δq, h·w)"]
        L5["⑤ Relax（RELAX_ITERATIONS=1，useBias=false）<br/>再解一遍法向（无 bias）<br/>+ 恢复系数 + 滚动阻力 + 摩擦"]

        L1 --> L2 --> L3 --> L4 --> L5
    end

    Sub --> Loop
    Loop --> Store["<b>StoreImpulses</b><br/>冲量写回 manifold（供下帧热启动）<br/>命中事件检测"]
```

**注意顺序的玄机**：

- **摩擦和恢复放在"松弛"阶段**（⑤），而不是和法向一起（③）。
  因为摩擦力的上限依赖法向力 `μ·Fn`，必须等法向冲量收敛了才算得准。
- **恢复系数（restitution）只在松弛阶段**（`useBias==false`）。
  这是 Box2D v3 的做法：先确保不穿模（③），再考虑弹跳（⑤）。

## 七、并行模型：任务、块、同步位

Box2D v3 的多线程模型有点特别（受 BepuPhysics2 启发，源码 `solver.h:1-48` 有长注释）。

```mermaid
flowchart TB
    subgraph Threads["线程/任务"]
        W0["worker 0<br/><b>orchestrator（编排者）</b><br/>推进 syncBits，自己也干活"]
        W1["worker 1<br/>spinner（自旋等待 + 偷活）"]
        W2["worker 2"]
        WN["worker N"]
    end

    subgraph Blocks["b2SyncBlock[]（每块一个原子计数器）"]
        B0["block0<br/>b2SolverBlock{start,count,type,color}<br/>atomic syncIndex"]
        B1["block1 …"]
        B2["block2 …"]
    end

    W0 -->|"b2AtomicStoreU32(&syncBits, 阶段|序号)"| All["所有 worker 原子读 syncBits"]
    All -->|"解码出 stageIndex + syncIndex"| B0
    B0 -->|"CAS(syncIndex: prev→cur) 成功者执行"| Work["执行该块的求解"]
```

### 三个巧妙之处

**① 每块一个原子计数器，而不是全局计数器**

```
❌ 全局 fetch_add：所有线程抢同一个缓存行 → 缓存行乒乓
✅ 每块独立 syncIndex：每个线程 CAS 自己的目标，落在自己的 L1
```

**② syncIndex 单调递增**

同一个 block 数组在多个子步/迭代中被复用。syncIndex 每轮 +1，
worker CAS `(prev, prev+1)`，所以主线程在迭代之间**完全不需要重置任何状态**，
也避免了 ABA 问题（`solver.h:216-221` 注释）。

**③ 起始偏移按 worker 编号错开 → L2 亲和性**

```
blocks:   [0] [1] [2] [3] [4] [5] [6] [7]
           ^           ^           ^   ^
           W0          W1          W2  W3   ← 起始偏移
```

W0 领 0→1→2→3，W1 领 4→5…… 负载均衡时每个 worker 每轮都命中同一段 block，
这段热数据就一直待在它的 L2 里。**CAS 失败说明邻居已经领走了，偷活者就停手**——
在轻微不均时保持局部性，同时还能排空队列。

### 块的类型（`b2SolverBlockType`）

```
一个颜色阶段的块布局：
   +------+------+------+------+------+------+
   |  J0  |  J1  |  C0  |  C1  |  C2  |  C3  |
   +------+------+------+------+------+------+
   ← graphJointBlocks →← graphContactBlocks →

类型标签在<b>块</b>上（不是阶段上）→ 关节块和接触块可以<b>在同一阶段并发跑</b>，中间不需要屏障。
```

## 八、岛屿（Island）：现在只为睡眠服务

v2 时代岛屿是**求解单位**（每个岛独立求解一次）。v3 改成了图着色求解，
**岛屿只剩下两个用途：睡眠判定和唤醒传播**。

```mermaid
flowchart TB
    subgraph I1["b2Island #5"]
        direction TB
        IA["bodies: [3, 7, 11]"]
        IB["contacts: [{c9,3,7}, {c12,7,11}]"]
        IC["joints: [{j4,3,11}]"]
        ID["constraintRemoveCount = 0"]
    end

    subgraph I2["b2Island #8（另一个岛）"]
        JB["bodies: [20, 21]"]
    end
```

**睡眠规则**（`solver.c:644-702` + `solver_set.c: b2TrySleepIsland`）：

```mermaid
flowchart TD
    S["对每个 awake 物体计算<br/>maxVelocity = |v| + |w|·maxExtent<br/>maxDeltaPos = |Δp| + |Δq.s|·maxExtent"]
    S --> SleepV["sleepVelocity = max(maxVelocity, 0.5·inv_dt·maxDeltaPos)"]
    SleepV --> Cmp{"sleepVelocity > sleepThreshold ?"}
    Cmp -->|"是"| Awake["sleepTime = 0<br/>保持清醒"]
    Cmp -->|"否"| Acc["sleepTime += dt"]
    Acc --> T{"sleepTime ≥ B2_TIME_TO_SLEEP(0.5s) ?"}
    T -->|"否"| Awake
    T -->|"是"| Mark["在 awakeIslandBitSet 里<br/><b>不</b>标记该岛为清醒"]
    Mark --> Island{"整岛所有物体<br/>都想睡？"}
    Island -->|"是"| Sleep["b2TrySleepIsland<br/>整体搬到新 sleepingSet"]
    Island -->|"否"| Awake

    Awake --> Note["注意：岛里<b>任何一个</b>物体醒着，<br/>整岛都醒着"]
```

> `0.5·inv_dt·maxDeltaPos` 这一项的意思是：**把"位置修正量"折算成一个等效速度**。
> 否则一个本该睡着的物体，因为求解器还在慢慢把它推出穿透，会一直被判定为"在动"。

### 岛屿分裂（`b2SplitIsland`）

如果一个岛里某个接触断了，岛可能已经**裂成两半**了。Box2D 不会立刻分裂（太贵），
而是：

1. 断接触时 `island->constraintRemoveCount++`
2. 睡眠时如果 `sleepTime ≥ 0.5s` 且 `constraintRemoveCount > 0` → 记录为**分裂候选**
3. **下一帧**在求解器启动前，用一个独立任务（`b2SplitIslandTask`）做并查集（union-find）重新划分

```mermaid
flowchart LR
    Before["岛 #5<br/>A—B—C—D<br/>（B—C 断了）<br/>constraintRemoveCount=1"]
    Before --> After["岛 #5: A—B<br/>岛 #9: C—D"]
```

> 源码 `island.c: b2SplitIsland`，用 `b2ContactLink{bodA,bodB}` 缓存，
> 让并查集过程完全不碰 `b2Contact`/`b2Joint`（缓存友好）。

## 九、内存管理：栈式分配器

每帧需要大量临时内存（约束数组、块数组、配对结果…）。Box2D 用**栈式分配器**（arena）：

```mermaid
flowchart LR
    subgraph Stack["world->stack（一块大内存）"]
        direction TB
        F1["帧 N：<br/>bulletBodies | stages | bodyBlocks<br/>graphBlocks | jointBlocks<br/>wideContactConstraints | overflowContacts"]
    end
    F1 -->|"b2StackFree 按<b>逆序</b>释放"| F1
    F1 -->|"帧末 b2StackAlloc 计数必须归零<br/>B2_ASSERT(b2GetStackAllocation(&stack)==0)"| OK["✓"]
    OK -->|"b2GrowStack：<br/>按需把栈扩到本帧峰值大小"| F1
```

**规则**：必须**后进先出**释放。好处是分配就是一次指针加法，O(1)，无碎片，无锁（每线程可以独立栈，或主线程统一分配）。
